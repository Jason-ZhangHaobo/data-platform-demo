# 数舵 Agent-first 产品蓝图

版本：1.0 · 2026-09-19。用途：为建设约8年的成熟证券数据中台提供智能化改造参考，不要求推倒经典模块。

## 一、产品判断

成熟数据中台的智能化不应等同于“在每个模块右侧加一个聊天框”。这种模式仍要求用户先理解菜单、对象和操作路径，Agent只是局部助手。

数舵采用两层产品结构：

1. **Data Agent智能工作台**：默认入口。用户只描述目标，Agent负责理解、澄清、规划、调用工具、生成产物、等待批准、继续执行并汇总证据。
2. **经典专业工作台**：数据源、同步、开发、调度、资产、质量、安全、服务、报表和运维继续独立可用；当用户需要逐字段配置、代码编辑或深度排障时从Agent结果中进入。

这吸收了两个当前官方产品信号：

- DataWorks新版Data Agent从旧侧边栏升级为独立全页面环境，强调多步规划、SQL/Python Coding、Skills、会话历史和关键节点确认。[DataWorks新版Data Agent](https://help.aliyun.com/zh/dataworks/user-guide/new-data-agent)
- Codex把目标、任务历史、环境、执行过程、产物和审阅组织在任务界面中，并支持后台并行和结果审阅，而不是要求用户先选择一个代码功能菜单。[Codex Cloud](https://developers.openai.com/es-419/docs/cloud)

数舵不复制两者视觉，而是把这些模式映射到证券数据中台。

## 二、独立界面信息架构

| 区域 | 内容 | 设计目的 |
|---|---|---|
| 左栏 | 新任务、任务历史、运行/等待/失败状态 | 用户按目标组织工作，不按模块组织 |
| 中央 | 对话、需求澄清、执行计划、工具活动、代码/配置/报表产物、批准卡片 | 在一个线程中完成端到端任务 |
| 右栏 | 工作空间、数据上下文、权限、预算、专业能力、证据 | 让Agent“为什么能做、使用什么、受什么限制”可见 |
| 底部输入 | 自然语言目标、上下文、技能、审批模式、发送 | 类似任务指挥台，而非搜索框 |

经典模块入口仍保留，但“专业工作台”是每一步的次要操作。主操作必须在当前会话执行或批准。

## 三、能力模型

Data Agent不直接获得超级权限。它编排与GUI/CLI/MCP共用的版本化原子API：

| 专业域 | Agent可做 | 关键关口 |
|---|---|---|
| 数据源/同步 | 读取元数据、生成映射/任务草稿、测试连接、运行受控同步 | 凭证、目标表、全量覆盖 |
| 实时 | 生成任务与恢复配置、查看Checkpoint/延迟 | 启停、回放、Topic权限 |
| 开发 | 生成/修改SQL和Python、真实调试、独立断言 | 高成本扫描、写入代码版本 |
| 调度发布 | 生成DAG和部署清单、演练、监控 | 工程师审阅、发布生产、回滚 |
| 资产治理 | 搜索、口径解释、血缘和影响分析、契约草稿 | 破坏性契约变更 |
| 质量 | 规则建议、实际检测、异常解释 | 新规则应用、阻断发布 |
| 安全 | 最小权限和脱敏策略草稿、访问原因解释 | 查询明细、审批、授权 |
| DAPI/XAPI | 设计、测试、文档和版本草稿 | 发布、应用授权、令牌 |
| 报表问数 | 数据集/指标/图表草稿、聚合查询 | 明细暴露、导出 |
| 运维 | 关联日志/批次/告警/血缘并生成诊断 | 执行恢复、重跑、资源扩容 |

## 四、审批模式

- **仅规划（PLAN_ONLY）**：分析、澄清和生成计划，不调用专业Agent或修改资源。
- **请求批准（REQUEST_APPROVAL）**：默认模式。每一步由用户点击执行；只读、草稿、运行、发布和授权分别显示状态。
- 专业步骤批准是后端持久资源，不是按钮视觉状态：绑定父意图、目标模块、目标摘要哈希和风险。创建或关联专业任务必须消费有效批准，刷新后仍显示APPROVED/BOUND及短证据ID。
- PLAN_ONLY无法通过API绕过界面关联已执行专业任务；步骤批准不等于草稿应用、运行、发布或授权。
- 后续再引入**智能审批**：仅在权限、成本、可回滚性和评测成熟后，允许低风险读操作自动执行；不直接提供无限权限模式。

## 五、当前第一版

已经落地：

- Data Agent成为默认首页和独立全页面三栏工作台；
- 任务历史、上下文、1—8步跨域计划、风险标签、活动状态和证据轨迹；
- 会话内可启动现有集成、实时、开发、资产、质量、安全、服务、报表、调度准备和运维专业Agent；
- 专业Agent完成后，可在会话中把受治理方案应用为草稿；
- 父意图与专业任务ID/类型持久关联，刷新或重新打开历史任务后可恢复专业任务状态和安全产物；
- REQUEST_APPROVAL步骤批准由GUI/API/CLI/MCP共享，绑定失败可复用已经创建的专业任务继续关联；
- 统一任务图从父意图、批准、交接和专业任务当前证据只读投影完成度，避免由React本地状态判断“已完成”；
- “停止后续编排”只取消尚未交接的父意图并撤销未消费批准；已有专业任务时要求分别控制子任务，不展示假取消；
- “记录接管并打开工作台”先幂等写入NO_EXECUTION交接，再进入经典模块，区分人工接管与专业Agent执行；
- 父任务图可取消仍在排队/运行的指定专业子任务；父意图与证据保留，完成态不允许伪取消；
- 同一步骤重试后的界面恢复严格使用任务图最新绑定，旧handoff只作历史证据，不参与当前状态竞争；
- 重启后的INTERRUPTED专业步骤可重新批准重试；父意图原文不持久化，因此只提示新建任务重新描述，不进行不可信自动重放；
- `shuduo-agent-tools/v1`向GUI/API/CLI/MCP公开十域风险、资源路径、依赖和批准边界，工具发现与执行授权严格分开；
- 模块页面降为可选人工接管入口；
- 任务原文不持久化，继承项目权限、预算和审计。

仍需继续：

- 为每种原子工具建立统一输入/输出Schema、风险、幂等和补偿协议；
- 支持Agent自动推进低风险步骤、并行步骤和失败后的受控重试；
- 将代码、同步任务、质量结果、DAPI/XAPI、报表和发布包以可展开Artifact呈现；
- 完成20条公网Agent-first E2E评测，而不是沿用模块流程成绩。

## 六、用于公司落地的参考方式

公司已有经典中台时，优先复用现有数据源、调度、权限、元数据、质量、发布和运维API。落地重点是：

1. 建立统一工具目录和风险分级，不让Agent直接操作数据库或绕过平台API；
2. 让同一Agent线程持有业务目标、上下文、计划、工具结果、批准和最终证据；
3. 先选“数据开发→调度发布→运维”标杆链路，再扩展全部专业域；
4. 用成功率、人工操作数、首次正确结果耗时、返工、成本和恢复能力验收，而不是统计聊天次数。
