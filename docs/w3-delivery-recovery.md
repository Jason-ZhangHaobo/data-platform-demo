# W3 私有交付提效方案

更新：2026-09-28。目标是先完成一条真实云端闭环，再扩大产品验收范围。

## 已确认的问题

1. 旧流程每次上传完整47MB控制面和319MB Worker包，未利用已存在的相同依赖。GitHub和本机单次PUT均失败；因此不能把故障简单归因于跨境网络。小Buffer请求与服务器内复制可工作，文件流、连接复用和整体传输时限仍需分别判断。
2. ossutil默认20秒请求超时、10次重试，缺少阶段诊断，使失败放大到20—35分钟。单纯增加外层超时不能解决底层请求反复失败。
3. 排查过度拆成多个小PR、重复全量验证，没有围绕可交付的关键链路组织。已有仓库工具和已记录的OAuth/FC兼容问题也未被充分复用。

## 已实施的纠正

- 控制面：比较旧包与新包完整字节，OSS内复制45,898,999字节，只上传962,623字节差异；随后完整下载验证SHA-256通过。
- Worker：核对902个不变ZIP条目，OSS内复制318,818,609字节，只上传103,634字节差异。服务端完整对象CRC64和字节数与本地新包一致；远端整包SHA-256尚未回证，明确保留此区别。
- 两个新对象均通过Bucket/Object ACL、Bucket Policy非公开、Block Public Access四项检查。部署使用FC原生`code.checksum`再次校验CRC64，不能只信任对象名或用户元数据。
- 后续更新、触发器、签名队列烟测和控制面切换合并为一个有界工作流；结果保存为单一脱敏报告。

## 下一步与通过标准

1. 更新现有私有Worker，保持规格、网络、秘密和并发边界，核对新包CRC64与环境。
2. 创建/核对唯一OSS jobs前缀触发器；提交一个固定签名虚构证券任务。部署身份仅获该任务的三个精确对象权限，不能写结果或获得FC Invoke。
3. 真实Spark3.5.9执行并通过独立断言，客户资产合计应为175.00。只有签名结果验证后才更新控制面并绑定该就绪批次。
4. 后续验证控制面真实启动、取消/超时/恢复，再做完整Agent生命周期评测。首条烟测不能计为85%完整E2E达标。

执行采用现有月度¥200预算门；最后本机账单核验为¥165.11，正式部署前再次查账。域名仍处于用户报告的备案审核期，不计为公网上线。

## 后续工作约定

按一个可验收结果组织一次迭代；功能变更做相关测试，合并前统一全量CI。独立只读检查可并行。每次失败先定位到具体请求和阶段，相同路径连续失败两次即改变已验证的技术路径。优先复用已有不可变产物和既有工具；已批准范围不重复请求用户确认。
